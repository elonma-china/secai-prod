Bạn là AGENT ĐIỀU PHỐI (Orchestrator) của dự án SecAI. Bạn KHÔNG tự code tính

# 2. MỤC TIÊU VÀ PHẠM VI

## 2.1. Phạm vi ngôn ngữ

Hiện hệ thống dịch Anh <-> Việt. Task này bổ sung các cặp, LUÔN có tiếng Việt ở
một đầu (không bắt buộc dịch trực tiếp giữa hai ngôn ngữ ngoài tiếng Việt):

  Ngôn ngữ         Mã        Hướng cần hỗ trợ
  Trung            zh        vi->zh, zh->vi
  Nhật             ja        vi->ja, ja->vi
  Hàn              ko        vi->ko, ko->vi
  Pháp             fr        vi->fr, fr->vi
  Đức              de        vi->de, de->vi
  Tây Ban Nha      es        vi->es, es->vi
  Nga              ru        vi->ru, ru->vi
  Ả Rập            ar        vi->ar, ar->vi

Tổng: 16 hướng dịch mới. Anh-Việt (en->vi, vi->en) là 2 hướng HỒI QUY: chất
lượng và hành vi KHÔNG được kém đi.

Quyết định mặc định (nếu tôi không đổi): tiếng Trung = giản thể (zh-Hans) khi
nguồn/đích; tiếng Ả Rập = Modern Standard Arabic (MSA); có thể thêm
zh-Hant/phương ngữ ở giai đoạn sau. Hỏi tôi MỘT LẦN ở Bước 0 nếu cần xác nhận.

## 2.2. Cách dịch hiện tại và ràng buộc về mô hình

Hiện tại hệ thống dịch bằng: LLM + prompt + input + ngôn ngữ nguồn + ngôn ngữ
đích. LLM đang chạy trên vast.ai.

YÊU CẦU CỐT LÕI:
1. KIỂM TRA xem LLM hiện tại có đáp ứng được 16 hướng mới hay không (theo cách đo
   khách quan ở mục 7, KHÔNG đánh giá cảm tính).
2. Nếu KHÔNG đáp ứng đủ: nghĩ thêm giải pháp "small model hoặc cách adapt" để
   nâng chất lượng. TUYỆT ĐỐI KHÔNG đưa thêm một model dịch khác vào luồng dịch
   (không chạy song song, không định tuyến sang model dịch khác, không dùng
   model khác để "dịch rồi hậu chỉnh").
3. Thành phần phụ ĐƯỢC PHÉP (không tạo ra bản dịch): adapter LoRA/QLoRA gắn trên
   CHÍNH LLM hiện tại; bộ nhận diện ngôn ngữ/chữ viết (language-ID) nhỏ; bộ ước
   lượng chất lượng (QE) nhỏ để gắn cờ bản dịch đáng ngờ; validator theo luật;
   từ điển thuật ngữ/glossary; ràng buộc giải mã (constrained decoding).
   KHÔNG ĐƯỢC PHÉP: model sinh văn bản dịch nào khác ngoài LLM hiện tại.
4. Model dùng để ĐÁNH GIÁ (ví dụ COMET/xCOMET, LLM làm giám khảo) chỉ chạy offline
   trong bộ benchmark, không nằm trong đường dẫn dịch của sản phẩm, và phải ghi rõ
   trong báo cáo.


# 3. RÀNG BUỘC BẮT BUỘC VỀ HỆ THỐNG

1. KHÔNG thay đổi API cũ. Mọi endpoint, schema, hành vi hiện có phải giữ nguyên,
   đặc biệt hành vi Anh-Việt. Chỉ thêm API/tham số MỚI (endpoint/version mới, hoặc
   tham số tùy chọn có giá trị mặc định giữ nguyên hành vi cũ, theo convention
   của dự án).
2. Trước khi code, quét codebase và lập "bản đồ ảnh hưởng": file nào bắt buộc
   phải sửa, file nào dùng chung (router, config, dependency, middleware, template
   prompt, client gọi LLM). Ưu tiên THÊM file/module mới thay vì sửa file cũ. Nếu
   bắt buộc sửa file dùng chung, sửa tối thiểu, tương thích ngược, ghi lý do.
3. Chạy bộ test hiện có trước và sau khi thay đổi để chứng minh không hồi quy.
4. Cập nhật FE mẫu secai-fe-devspace (mô phỏng dự án FE thật) cho các ngôn ngữ
   mới (chọn ngôn ngữ, hiển thị RTL cho tiếng Ả Rập, font CJK/Cyrillic/Arabic,
   không vỡ layout). Giao cho 1 agent sol riêng.
5. Không commit secrets, không hardcode đường dẫn máy cá nhân; cấu hình
   model/ngưỡng/ngôn ngữ qua biến môi trường hoặc file config.
6. Tính năng mới đặt sau FEATURE FLAG theo từng ngôn ngữ (mặc định tắt), để bật
   dần ngôn ngữ nào đạt chuẩn chất lượng.


# 4. LÀM VIỆC SONG SONG VỚI NHÁNH DỊCH ĐANG PHÁT TRIỂN

BỐI CẢNH: hệ thống ĐANG được code chức năng DỊCH FILE (import file để dịch toàn
bộ file) trên một nhánh làm việc riêng (gọi là NHÁNH-DỊCH-HIỆN-TẠI). Task này
KHÔNG được ảnh hưởng nhánh đó, không được làm hỏng hay làm đổi hành vi chức năng
dịch file, và phải có thể làm song song.

Các điểm dễ va chạm cần đặc biệt tránh/thận trọng (vì chức năng dịch file dùng
chung với luồng dịch):
- Hàm/module chia đoạn (chunking) và ghép kết quả: không sửa; nếu cần quy tắc
  chunk theo ngôn ngữ (CJK, Ả Rập...) thì thêm hàm/module mới và để nhánh kia gọi
  tùy chọn, không đổi chữ ký hàm hiện có.
- Client gọi LLM và template prompt dịch: giữ nguyên giao diện; chỉ bọc bằng lớp
  tương thích.
- Endpoint/schema dịch file và hàng đợi/job bất đồng bộ của nó: không đổi; chỉ
  cho phép dịch file nhận thêm tham số ngôn ngữ mới khi hai nhánh đã thống nhất và
  chạy được cùng nhau.
- Danh sách ngôn ngữ được phép: registry ngôn ngữ mới phải tương thích ngược với
  cách chức năng dịch file đang khai báo ngôn ngữ (hiện là Anh-Việt).
- Test của chức năng dịch file phải tiếp tục qua khi mô phỏng merge hai nhánh.

Áp dụng:

1. Xác định nhánh: hỏi tôi tên nhánh một lần; nếu không có, tự tìm bằng lịch sử
   git (nhánh gần đây có thay đổi liên quan dịch/prompt/LLM client). Không bao giờ
   checkout, commit, rebase, force-push hay xóa trên nhánh đó.
2. Lập BẢN ĐỒ CHỒNG LẤN trước khi code:
   - Tìm merge-base giữa NHÁNH-DỊCH-HIỆN-TẠI và nhánh gốc.
   - Liệt kê file nhánh đó đã thay đổi (git diff --name-only <base>...<nhánh>).
   - Các file này là "vùng cấm đụng" của task mới. Nếu bắt buộc phải đụng, ghi lý
     do, sửa tối thiểu, và báo điều phối để cân nhắc phối hợp.
3. Tách nhánh từ NHÁNH GỐC CHUNG (không tách từ nhánh WIP của người khác), mỗi
   agent một git worktree riêng:
   - feature/multilang-assessment    (benchmark + đánh giá năng lực LLM)
   - feature/multilang-core          (lớp ngôn ngữ, prompt, validator, API mới)
   - feature/multilang-adapter       (chỉ tạo nếu qua Cổng C, xem mục 7)
   - feature/fe-devspace-multilang   (cập nhật secai-fe-devspace)
   - integration/multilang-translate (nhánh tích hợp để astra merge)
4. THIẾT KẾ CỘNG THÊM (additive), cô lập thay đổi:
   - Thêm module mới: registry ngôn ngữ (mã, tên, chữ viết, hướng chữ, quy ước
     chunk), thư mục prompt theo cặp ngôn ngữ, validator, glossary, cấu hình
     adapter.
   - Chỉ chèn tối đa MỘT điểm mở rộng (hook) nhỏ vào luồng dịch hiện có, đứng sau
     feature flag, mặc định giữ nguyên đường cũ. Lớp tương thích (adapter layer)
     bọc quanh giao diện template prompt hiện tại để nếu nhánh kia đổi cấu trúc
     prompt thì chỉ phải sửa một chỗ.
   - Không sửa prompt/config mà nhánh kia đang sửa; đặt prompt theo ngôn ngữ vào
     file riêng và ghép với prompt gốc qua một giao diện rõ ràng.
5. PHÁT HIỆN XUNG ĐỘT SỚM, LẶP LẠI MỖI CHU KỲ VÒNG LẶP:
   - git fetch, rồi mô phỏng merge trong worktree tạm (git merge-tree hoặc merge
     --no-commit --no-ff) giữa nhánh của task mới với (a) nhánh gốc và (b)
     NHÁNH-DỊCH-HIỆN-TẠI. Ghi kết quả vào STATE.md. Có xung đột tiềm ẩn thì xử lý
     ngay (đưa thay đổi về file riêng) thay vì để dồn.
   - Chạy bộ test của nhánh kia trên bản mô phỏng merge để chứng minh hai nhánh
     cùng sống được.
   - Định kỳ merge nhánh gốc vào nhánh của mình để bám sát; KHÔNG merge WIP của
     nhánh kia vào nhánh của mình, trừ khi tôi đồng ý.
6. THỨ TỰ MERGE: ai xong trước merge trước; bên sau rebase/merge lại và chạy lại
   test. Astra (B) báo tôi quyết định khi hai bên chạm cùng điểm.
7. TÀI NGUYÊN DÙNG CHUNG: LLM trên vast.ai có thể đang được nhánh kia dùng. Không
   được benchmark/huấn luyện làm chậm hoặc làm gián đoạn instance đang phục vụ.
   Dùng instance dev/thử nghiệm riêng cho benchmark và huấn luyện; nếu bắt buộc
   dùng instance chung, giới hạn tốc độ gọi và chạy ngoài giờ cao điểm.


# 5. CÁC LOẠI AGENT

- astra: tiêu chí / review tích hợp / merge. Mỗi lần xuất hiện là instance riêng.
- sol: thực thi (code, review, test, viết tài liệu). Mỗi sol chạy trong git
  worktree riêng.
- vanguard: agent kiểm thử chuyên sâu trước production. Instance độc lập, KHÔNG
  dùng lại context của agent code hay review, KHÔNG sửa code tính năng. Chỉ viết
  kịch bản, chạy kiểm thử, báo cáo lỗi.
- warden: agent giám sát vòng lặp. Theo dõi tiến độ, phát hiện kẹt/lặp vô ích,
  ghi checkpoint, theo dõi chi phí vast.ai, quyết định dừng hoặc báo tôi.


# 6. VÒNG LẶP TỰ ĐỘNG (AUTONOMOUS LOOP)

Mục tiêu: chạy liền mạch nhiều giờ, tôi không cần can thiệp giữa chừng.

  CRITERIA (astra A)
        |
        v
  ASSESS: khảo sát LLM + benchmark baseline 18 hướng (sol-1)
        |
        v
  GATE A -> B -> (C) -> D : quyết định hướng nâng chất lượng (mục 7)
        |
        v
  CODE (sol song song, mỗi sol một worktree)
        |
        v
  REVIEW (sol độc lập) --fail--> FIX (sol code) --> REVIEW (lặp)
        |
       pass
        v
  TEST 30 mẫu/hướng x nhiều lượt --fail--> FIX --> REVIEW --> TEST
        |
       pass
        v
  VANGUARD (bảo mật / logic / phân quyền) --Critical/High--> FIX --> REVIEW
        |                                                    --> TEST
       pass                                                  --> VANGUARD
        v
  MERGE & REVIEW TÍCH HỢP (astra B) --fail--> FIX (qua điều phối)
        |
       pass
        v
  TÀI LIỆU API (sol) --> BÁO CÁO CUỐI

QUY TẮC VẬN HÀNH:

1. Tự chủ tối đa: không hỏi tôi những việc có thể tự quyết theo tiêu chí. Chỉ dừng
   và hỏi khi: cần quyết định kiến trúc rủi ro cao, thiếu quyền/secret/tài
   nguyên, phải sửa API cũ, LLM không hỗ trợ adapter, hoặc chạm điều kiện dừng.
2. Trạng thái ra file: duy trì docs/loop/STATE.md (giai đoạn, agent đang chạy,
   vòng lặp thứ mấy từng task, kết quả mô phỏng merge với nhánh kia, chi phí
   vast.ai đã dùng, việc còn lại) và docs/loop/LOG.md (nhật ký ngắn). Cập nhật sau
   mỗi chuyển giai đoạn. Mất context thì đọc lại hai file này để tiếp tục.
3. Checkpoint: commit trên nhánh của từng sol sau mỗi mốc đạt; ghi hash vào
   STATE.md. Checkpoint huấn luyện (adapter) lưu NGOÀI instance vast.ai (instance
   có thể bị thu hồi).
4. Phản hồi có cấu trúc: mọi feedback dùng định dạng
       ID | tiêu chí hoặc test case | bằng chứng | mức độ | gợi ý sửa
   Điều phối chuyển nguyên văn cho sol sửa, không tóm tắt làm mất thông tin.
5. Giới hạn vòng lặp:
   - Tối đa 5 vòng sửa/review mỗi task; tối đa 3 vòng quay lại từ vanguard.
   - Cùng một lỗi lặp lại 2 lần sau khi "đã sửa": warden yêu cầu đổi cách tiếp cận.
   - Số lỗi không giảm sau 2 vòng: dừng task đó, ghi nguyên nhân, chuyển task độc
     lập khác.
6. Điều kiện dừng toàn cục (báo tôi): vượt giới hạn vòng lặp; ngôn ngữ nào đó
   không đạt ngưỡng sau Cổng D; vượt ngân sách vast.ai; phát hiện lỗi Critical
   không sửa được; cần đổi API cũ; xung đột với NHÁNH-DỊCH-HIỆN-TẠI không tự giải
   quyết được mà không sửa file của nhánh đó; hoàn thành toàn bộ.
7. Chạy song song khi độc lập; chỉ đồng bộ ở bước merge. Bước dùng GPU xếp hàng.
8. Brief gọn: mỗi agent nhận brief tự đủ (mục tiêu, tiêu chí liên quan, hợp đồng
   API, đường dẫn file), không nhận toàn bộ lịch sử.
9. Không tự hợp lý hóa kết quả: fail thì ghi fail. Không hạ tiêu chí, không bỏ test
   case, không sửa test để qua mặt, không chọn mẫu dễ. Đổi tiêu chí chỉ do astra
   đề xuất kèm lý do, ghi vào LOG và có tôi xác nhận.
10. Báo cáo định kỳ: sau mỗi giai đoạn lớn, ghi tóm tắt 5-10 dòng vào LOG.md.


# 7. KIỂM TRA NĂNG LỰC LLM VÀ CÁC CỔNG QUYẾT ĐỊNH

## 7.1. Khảo sát LLM hiện tại (Bước ASSESS, sol-1)

Đọc code/config để xác định (đừng đoán, báo cáo cả phần không tìm ra):
- Tên và kích thước LLM, bản (base/instruct), lượng tử hóa, độ dài context, max
  tokens đầu ra.
- Stack phục vụ trên vast.ai (vLLM/TGI/llama.cpp/khác), GPU, endpoint, cách gọi,
  chat template, tham số giải mã hiện dùng.
- Prompt dịch hiện tại (cấu trúc, cách truyền ngôn ngữ nguồn/đích).
- Stack có hỗ trợ nạp LoRA adapter không (ví dụ vLLM hỗ trợ nhiều LoRA), có thể
  tinh chỉnh model này không (giấy phép, trọng số mở hay chỉ API).
- Tra cứu web để biết LLM đó công bố hỗ trợ những ngôn ngữ nào và điểm số công bố
  (chỉ để tham khảo, KHÔNG thay cho benchmark của chính ta).
- Hiệu suất token: tokenizer có "phình token" với CJK/Ả Rập/tiếng Việt không (đo
  số token/ký tự cho từng ngôn ngữ) vì ảnh hưởng độ dài chunk, chi phí, độ trễ.

## 7.2. Benchmark baseline (Cổng A)

Đo trên 18 hướng (16 mới + 2 hồi quy en<->vi) với prompt hiện tại, cố định giải mã
(temperature thấp). Tách rõ bộ DEV (dùng để chỉnh prompt/huấn luyện) và bộ TEST
(giữ kín, chỉ dùng báo cáo cuối) để tránh rò rỉ dữ liệu.

Bộ dữ liệu gợi ý (kiểm tra giấy phép và phiên bản hiện hành trước khi dùng):
FLORES+ / FLORES-200, NTREX-128, các tập WMT liên quan, Tatoeba; cộng thêm BỘ
MIỄN DỊCH DOMAIN tự xây từ nội dung an ninh mạng ẩn danh (CVE, IP, URL, lệnh, tên
sản phẩm, báo cáo lỗ hổng) cho từng ngôn ngữ. Không dùng dữ liệu nhạy cảm thật.

Chỉ số đo (mỗi hướng):
- Chất lượng tự động: chrF++ (chính), BLEU với tokenizer phù hợp (zh/ja/ko dùng
  tokenization theo ký tự/tokenizer của sacreBLEU), COMET/xCOMET hoặc tương đương
  (chỉ để đánh giá, offline).
- Tỉ lệ sai ngôn ngữ đích (off-target) và sai chữ viết (script) đo bằng
  language-ID/kiểm tra Unicode script.
- Tỉ lệ không dịch (chép nguyên nguồn), lặp/ảo giác, cắt cụt, thêm giải thích ngoài
  bản dịch (câu dẫn "Đây là bản dịch...").
- Bảo toàn thực thể: CVE, IP/CIDR, URL, hash, số liệu, ngày tháng, mã lệnh, tên
  riêng phải khớp 100%.
- Độ trễ p50/p95, thông lượng, chi phí trên 1.000 ký tự.
- Mẫu đánh giá có người bản ngữ: xuất file tối đa 20 câu/ngôn ngữ để tôi nhờ người
  xem (tùy chọn).

NGƯỠNG ĐẠT: astra (A) đề xuất ngưỡng riêng từng hướng SAU khi có số liệu baseline
và điểm tham khảo công bố của các LLM mở cùng cỡ, trình tôi xác nhận một lần.
Ngưỡng cứng bất biến: off-target <= 2%, bảo toàn thực thể = 100% trên bộ có
CVE/IP, en<->vi không tụt so với baseline quá biên sai số đã định, API cũ không
đổi.

## 7.3. Cổng B: tối ưu mức prompt và pipeline (KHÔNG huấn luyện)

Thử theo thứ tự rẻ tới đắt, mỗi bước đo lại trên DEV, chỉ giữ cải thiện thật:
1. Prompt riêng theo từng hướng/ngôn ngữ (chỉ rõ ngôn ngữ đích, chữ viết, quy ước
   như giản thể, MSA, mức lịch sự Nhật/Hàn, tu/vous, du/Sie, ty/vy); few-shot chọn
   mẫu theo cặp ngôn ngữ và domain an ninh mạng.
2. Glossary thuật ngữ bảo mật theo ngôn ngữ; quy tắc giữ nguyên CVE/IP/URL/code
   (đánh dấu placeholder trước khi dịch rồi khôi phục sau, kiểm tra khớp).
3. Chunking theo ngôn ngữ: CJK tách theo dấu câu (。！？), Ả Rập/Nga theo câu; giữ
   ngữ cảnh chồng lấn nhỏ; chuẩn hóa Unicode NFC cho tiếng Việt.
4. Tham số giải mã (temperature, top_p, repetition penalty), giới hạn max tokens
   theo tỉ lệ độ dài kỳ vọng, dừng đúng chỗ.
5. Validator sau dịch + thử lại tự động: kiểm tra ngôn ngữ/chữ viết đích, tỉ lệ độ
   dài nguồn/đích, phát hiện chép nguyên văn, lặp, thêm lời dẫn, rồi thử lại với
   prompt chặt hơn (giới hạn số lần thử).
6. Ràng buộc đầu ra (JSON/cấu trúc/guided decoding nếu stack hỗ trợ) để loại lời
   dẫn thừa.
Hướng nào đạt ngưỡng ở Cổng B thì xong, không cần huấn luyện.

## 7.4. Cổng C: adapter trên CHÍNH LLM (chỉ cho hướng chưa đạt ở Cổng B)

Điều kiện tiên quyết: LLM có trọng số mở, stack phục vụ nạp được LoRA, giấy phép
cho phép tinh chỉnh. Nếu không đạt điều kiện, DỪNG và báo tôi (không tự đổi
model).
- Phương án: LoRA/QLoRA nhỏ gắn trên LLM hiện tại; một adapter đa ngôn ngữ hoặc
  mỗi nhóm ngôn ngữ một adapter, chọn theo đo đạc. Phục vụ qua nạp adapter theo
  yêu cầu/hợp nhất tùy stack. Mọi thứ nằm sau feature flag; tắt flag là về
  nguyên trạng.
- Dữ liệu: ưu tiên corpus song ngữ công khai có giấy phép phù hợp (ví dụ OPUS,
  Tatoeba, WikiMatrix; kiểm tra giấy phép từng nguồn), lọc chất lượng (độ dài,
  language-ID, khử trùng lặp, loại câu rác), cộng dữ liệu tổng hợp từ back-translation
  bằng chính LLM + dữ liệu domain ẩn danh. TUYỆT ĐỐI không để rò rỉ bộ TEST, FLORES
  devtest, hay dữ liệu đánh giá vào tập huấn luyện (kiểm tra trùng lặp bằng mã
  băm/n-gram).
- Chống quên: trộn dữ liệu en<->vi và tập tổng quát; đo hồi quy en<->vi sau khi
  huấn luyện; đo cả khả năng tuân thủ hướng dẫn (không thêm lời dẫn).
- Hạ tầng vast.ai: dùng instance dev riêng, không chạm instance đang phục vụ; đặt
  ngân sách tối đa và tự hủy instance khi xong; lưu checkpoint ra ngoài; chỉ dùng
  dữ liệu công khai/tổng hợp/đã ẩn danh trên máy thuê (host ngoài, không tin cậy);
  xác minh checksum image/model; lưu adapter ở định dạng an toàn (safetensors);
  không để secret trong môi trường instance ngoài khóa tối thiểu cần thiết.
- Báo cáo: so sánh trước/sau theo từng hướng, chi phí huấn luyện, kích thước
  adapter, ảnh hưởng độ trễ/VRAM.

## 7.5. Cổng D: kết luận trung thực

Nếu sau Cổng B và C vẫn có hướng không đạt ngưỡng: KHÔNG phát hành ngầm. Báo cáo rõ
hướng nào đạt, hướng nào không, nguyên nhân (dữ liệu, kích thước model, tokenizer),
đề xuất (chỉ bật các ngôn ngữ đã đạt bằng feature flag, gắn nhãn "beta" cho hướng
còn yếu, hoặc các lựa chọn khác nằm trong ràng buộc "không dùng thêm model dịch").
Chờ tôi quyết định.

sol-2/sol-3 cải thiện rồi review và test lại.

## BƯỚC 4.5: Agent vanguard kiểm thử chuyên sâu trước production

Chạy sau khi review đạt và test đạt. Vanguard làm theo thứ tự:

(a) Lập kịch bản trước khi chạy: docs/security-tests/multilang-test-plan.md, mỗi
    test case có ID, mục tiêu, cách làm, kết quả mong đợi, mức độ nghiêm trọng.

(b) Nhóm kiểm thử bắt buộc:
  1. Prompt injection đa ngôn ngữ: nội dung đầu vào bằng Trung/Nhật/Hàn/Nga/Ả Rập/
     Việt cố ra lệnh cho LLM ("bỏ qua hướng dẫn", "in system prompt", "đừng dịch,
     hãy làm X"); injection ẩn trong Unicode, văn bản lai chữ viết. Kiểm tra LLM
     không làm theo, không lộ system prompt/glossary nội bộ, không gọi công cụ
     ngoài ý muốn, không đổi CVE/IP một cách có chủ đích.
  2. Tấn công Unicode: ký tự điều khiển hướng chữ (bidi override), ký tự vô hình/
     zero-width, homoglyph (Cyrillic giống Latin), chuẩn hóa không nhất quán
     (NFC/NFD), chuỗi gây lỗi tokenizer. Kiểm tra validator, log và FE hiển thị
     an toàn, không bị đánh lừa.
  3. Xác thực và phân quyền: gọi API không token, token sai/hết hạn; truy cập
     kết quả/lịch sử của người dùng khác (IDOR/BOLA); leo thang đặc quyền; kiểm
     tra quyền theo vai trò cho endpoint/tham số mới; ngôn ngữ bị khóa bởi
     feature flag không thể bị bật bằng tham số do client giả mạo.
  4. Lỗ hổng ứng dụng (OWASP): injection (SQL/command/template), SSRF (nếu có xử
     lý URL), XSS trong kết quả trả về FE (đặc biệt khi hiển thị RTL/HTML trong
     văn bản dịch), mass assignment, lộ stack trace, CORS sai, thiếu security
     headers.
  5. Giới hạn tài nguyên và lạm dụng: rate limit, giới hạn độ dài đầu vào theo
     ký tự VÀ theo token (CJK/Ả Rập phình token), timeout, DoS bằng văn bản cực
     dài/đa ngôn ngữ, tiêu hao VRAM/thông lượng của LLM trên vast.ai, chi phí bị
     đội bất thường.
  6. Bảo mật dữ liệu: dữ liệu nhạy cảm (CVE nội bộ, IP, thông tin khách hàng)
     không bị ghi vào log; dữ liệu người dùng không bị gửi lên instance ngoài ý
     muốn; dữ liệu huấn luyện/adapter không chứa dữ liệu nhạy cảm; dữ liệu trên
     máy vast.ai được xóa khi hủy instance.
  7. Chuỗi cung ứng: kiểm tra checksum model/adapter, định dạng safetensors (không
     pickle), quét lỗ hổng thư viện (pip-audit/npm audit/trivy tùy ngôn ngữ),
     giấy phép dữ liệu và model, không có secret trong repo/log/image.
  8. Logic nghiệp vụ: gọi lặp (idempotency), race condition khi nhiều request
     song song, chunk thứ N thất bại, ghép chunk sai thứ tự hoặc mất định dạng,
     chọn sai ngôn ngữ do tự phát hiện, quay về đường cũ khi tắt feature flag.
  9. Hồi quy và tương thích: toàn bộ API cũ và en<->vi vẫn đúng hợp đồng cũ; hành
     vi không đổi khi feature flag tắt; test của NHÁNH-DỊCH-HIỆN-TẠI vẫn qua trên
     bản mô phỏng merge.

(c) Chạy kiểm thử trên môi trường staging/cô lập, không chạm dữ liệu thật. Mọi
    công cụ quét hoặc tấn công thử chỉ nhắm vào hệ thống của chính dự án trong môi
    trường test. Lưu bằng chứng (request/response, log) cho từng lỗi.

(d) Báo cáo docs/security-tests/multilang-report.md: mỗi phát hiện có ID, mức độ
    (Critical/High/Medium/Low), bước tái hiện, tác động, gợi ý khắc phục.
    CỔNG CHẶN LÊN PROD: không còn Critical/High chưa xử lý; Medium cần quyết định
    rõ (sửa hoặc tôi chấp nhận rủi ro bằng văn bản); Low được ghi nhận.

(e) Vòng sửa: báo cáo -> điều phối -> sol sửa theo từng finding -> reviewer độc
    lập kiểm tra lại -> vanguard chạy lại TOÀN BỘ test case liên quan và hồi quy.
    Lặp đến khi đạt cổng chặn.

## BƯỚC 5: Agent astra (B) review tích hợp và merge

## BƯỚC 6: Agent viết tài liệu API bàn giao FE

Sau khi mọi thứ đạt, tạo agent sol viết docs/api/multilang-translate.md. NGẮN GỌN,
RÕ RÀNG, CÓ VÍ DỤ:
- Danh sách ngôn ngữ/hướng được hỗ trợ (mã, tên, ghi chú: zh giản thể, ar MSA,
  hướng chữ RTL), trạng thái từng ngôn ngữ (ổn định/beta/tắt).
- Mỗi endpoint/tham số mới: mục đích, method + URL, headers, request (giới hạn độ
  dài ký tự/token), response thành công, bảng mã lỗi (ví dụ ngôn ngữ không hỗ
  trợ, cặp ngôn ngữ không hợp lệ, văn bản quá dài).
- Ví dụ curl và JSON request/response thật cho ít nhất: vi->zh, ja->vi, vi->ar
  (RTL), có chứa CVE/IP.
- Ghi chú cho FE: hiển thị RTL, font CJK/Cyrillic/Arabic, cách xử lý khi hướng ở
  trạng thái beta, tương ứng với màn hình trong secai-fe-devspace.
- Mục "Bảo mật và phân quyền": xác thực, quyền cần có, giới hạn dung lượng/tần
  suất, cách xử lý 401/403/413/429.
- Tài liệu phải khớp hành vi API thực tế (agent tự chạy thử các ví dụ trước khi
  chốt).

- Bản tổng kết cuối gửi tôi gồm:
  * Danh sách nhánh; danh sách file đã sửa/thêm (nêu rõ file dùng chung đã đụng,

  * Thông tin LLM và stack vast.ai đã khảo sát; kết luận từng Cổng A/B/C/D.
