# Multilang assessment harness

This directory contains CPU validation/scoring and a serial runner for the existing Vast DuyTa translator. It does not ship corpus gold, a judge model, or a production route. Live model work remains blocked until a coordinated GPU reservation, corpus and attested configuration exist; the OCR task has stopped its own helper, and all three auxiliary model trials are used.

Use a private virtual environment. Install the repository dev extra, pytest-timeout and the optional Redis extra needed by existing test fixtures; install the pinned, hash-locked metric dependency from requirements.lock. OpenSSL with Ed25519 `pkeyutl -rawin` support is required for signed tester evidence. No dependency is added to the shared pyproject.

    uv venv .venv
    uv pip install --python .venv/bin/python -e '.[dev]' pytest-timeout redis==8.0.1
    uv pip install --python .venv/bin/python --require-hashes -r evals/multilang/requirements.lock
    .venv/bin/python -m pytest -q tests/multilang_assessment

Corpus JSONL rows require id, direction, source, reference, split, stratum, protected_spans, source_revision, license, source_group and **aligned_item_id** from the trusted source dataset. A live row also requires data_classification to be public or anonymized. Protected spans are nonoverlapping source-codepoint offsets with exact text and kind. The validator rejects cross-split document groups, cross-language/reversed rows bearing the same aligned item ID in different splits, normalized duplicates under different IDs, and near duplicates. The minimum quota counts distinct source groups per direction; 30 rows from one group are insufficient. The ID is still supplied data, so the live runner and hard score gates require a tester-signed alignment map bound to the entire manifest hash. The validator requires all 18 directions by default:

    .venv/bin/python -m evals.multilang.validate_corpus corpus.jsonl --min-per-direction 30

References must come from an independently curated, licensed revision. The FLORES+ registry in source-registry.json is metadata only; access conditions have not been accepted here, so there is no data file to run. Keep all directions/reversals of a source document in one split. Keep devtest in tester custody as sealed TEST. Add independently reviewed security-domain references; no candidate translation becomes gold.

The runner has model-only, legacy-api and multilang-api modes. It schedules all 18 directions, en/vi controls, and the 16 new directions respectively. Without --live it prints a plan and makes no network call or result file:

    .venv/bin/python -m evals.multilang.run --manifest corpus.jsonl --mode model-only --split DEV --rounds 1 --output dev-results.jsonl

Live execution additionally requires a frozen inventory, a tester-signed alignment map, a tester-signed active shared lease released by OCR, bounded requests/rate/time/worst-case cost, a new output path, and a common nonblocking lock in the protected tester ledger held across the entire live run. Distinct signed lease files therefore cannot run concurrently on the same assessment slot. Model-only requires frozen prompt and decoding files, probes /v1/models, and accepts only the verified incumbent DuyTa endpoint; it accepts exactly one assistant response and rejects non-null tool/function markers at the response, choice and message levels. The fixed model-only request includes `chat_template_kwargs: {"enable_thinking": false}`, matching the accepted gateway provider; the fixed field is included in the config hash. The prompt file and approved temperature/top_p/max_tokens/seed values are also bound by that hash. A prior run without the fixed field is a different configuration and must not be pooled with new results. Decoding accepts only finite temperature/top_p, bounded max_tokens and optional seed; it cannot replace model, messages, stream or add tools. API modes require an independent gateway-model attestation in their inventory. The API key, if required, comes only from MULTILANG_ASSESSMENT_API_KEY in process environment and is never written to results. Before every request the runner rereads and verifies the signed lease after rate-limit sleep, checking the remaining request count; the async HTTP probe and POST are bounded by an absolute wall deadline no later than the remaining lease time. A signed lease binds one run ID, exact phase and total scheduled request count, corpus/config/inventory/alignment digests and the output destination binding (resolved path plus protected parent device/inode). The runner holds that parent directory descriptor and creates output relative to it with no-follow/exclusive flags, so a changed ancestor symlink cannot redirect the write. An exclusive-create ledger claim consumes the lease before any network call. TEST additionally binds the corpus seal, candidate config and tester-issued holdout ID; the holdout is retired before the run claim so interruption cannot make it reusable. These are local admission checks and do not replace the resource owner's approval/scheduling. No assessment live call has been made.

The tester must provision `MULTILANG_TESTER_PUBKEY_PATH` and pin its SHA-256 in `MULTILANG_TESTER_PUBKEY_SHA256` outside the untrusted corpus/review/lease files. The tester also provisions `MULTILANG_TESTER_LEDGER_DIR` on durable storage. The runner rejects missing or group/world-writable key, ledger and output-parent paths, symlinked final paths, invalid signatures and reused claim IDs. Evidence envelopes have exactly `payload` and `signature_b64`; `payload.schema` is `multilang-evidence-v1`, and kinds are `alignment-map`, `run-lease`, `review-bundle` and `en-vi-margin-policy`. Signatures cover canonical UTF-8 JSON (sorted keys, compact separators, no NaN) using Ed25519. The tester must retain the private key outside this repository; the code cannot prove reviewer qualification merely from a valid signature. The OS/operator must protect the configured key, its parent path, output parent and ledger against tampering by untrusted processes, including same-user writes or deletion; the local ledger is not a remote append-only authority. If that trust boundary is unavailable, live evidence remains blocked. Test fixtures create disposable keys only in pytest temporary directories.

Score with a separate JSONL of blind review annotations and tester-issued attestations:

    .venv/bin/python -m evals.multilang.score --manifest corpus.jsonl --results dev-results.jsonl --annotations reviews.jsonl --alignment-attestation alignment.json --review-attestation review-bundle.json --mode model-only --phase DEV --rounds 3 --output dev-score.json

Each annotation uses sample_id, round, **output_sha256 of the exact validated output**, decision (pass/fail/uncertain), reviewer, blind=true, calibration_id, off_target, and a rubric object with boolean target_variant, meaning_preserved, no_hallucination, readable, register_appropriate and literals_preserved. A signed review bundle binds the manifest, exact results and annotations hashes plus reviewer/calibration IDs and tester attestation of blind qualification. Stale/missing/uncertain reviews cannot pass. Without both verified alignment and review attestations, 30 distinct sources per direction and three complete rounds, the hard `quality_gate` and `off_target_gate` remain BLOCKED. The CLI's `--min-samples-per-direction` changes only descriptive `rubric_threshold_gate` and `off_target_threshold_gate`; it cannot relax hard minima. The scorer matches result data hash, model ID/revision and prompt/config hashes, counts missing/error rows in every scheduled denominator, reports 30 distinct source groups per direction/round, Wilson intervals based on unique source groups, protected literal mismatches per sample (hashes rather than raw values), chrF++/BLEU signatures, heuristic script/copy/repetition/preamble/truncation rates and review-derived hallucination rate with coverage, usage/cost coverage, and latency/throughput. Unsupported protected kinds are `entity_gate=BLOCKED`. The release gate remains BLOCKED until independent corpus/reviewer, en/vi non-inferiority margin, sealed TEST, security and integration gates are satisfied.

For en↔vi paired descriptive evidence, supply the legacy-api control results and output-bound reviews alongside the model-only candidate:

    .venv/bin/python -m evals.multilang.score --manifest corpus.jsonl --results candidate.jsonl --annotations candidate-reviews.jsonl --baseline-results legacy.jsonl --baseline-annotations legacy-reviews.jsonl --alignment-attestation alignment.json --review-attestation candidate-review-bundle.json --baseline-review-attestation baseline-review-bundle.json --margin-attestation frozen-margin.json --mode model-only --phase DEV --rounds 3 --output paired-report.json

The paired bootstrap resamples source-document groups with 10,000 fixed-seed replicates. It requires both en↔vi directions and complete result/review pairs. A tester-signed margin policy must bind the exact corpus and completed baseline results, declare a finite margin, `bonferroni-two-directions` with familywise alpha 0.05, and be timestamped after baseline completion but before every candidate start. With both verified review bundles, 30 independent source groups per direction and three rounds, the one-sided 97.5% lower bound for each direction can pass or fail the frozen margin. Missing evidence leaves non-inferiority BLOCKED. This scoped gate does not confer production release.

The scorer never calls the live model. It does not claim that chrF++ or BLEU is a 70% quality pass rate, or that declared reviewer IDs prove qualified independent evaluation.
